1The idea

Trade Wars becomes the first game you play without leaving Claude Code: a pane beside the transcript shows your empire, custom tools make the moves, and a cheap model plays the turns while a strong model sets the strategy.

The claim worth testing is not "an LLM can play a game". It is that a game can be designed so a small model plays it well. Trade Wars suits this: the move set is tiny, the state is numeric, and the optimal move is usually arithmetic over reserves and upgrade costs. That is a Haiku-shaped problem, not an Opus-shaped one.

The educational value of the repo grows with it. Today it teaches full-stack Sui development. With this, it also teaches how to build an agent-native client and how to cut token cost by design.

2What a mod is

A mod is a Claude Code plugin whose body is one register(on) file. It hooks about 35 engine events. At each event it can let the call pass (next(e)), change it, or answer it itself. Anthropic ships four mods inside the binary and publishes their source at anthropics/claude-code/tree/main/mods.

The relevant powers for Trade Wars:

3The three-tier model economy

This is the core of the design. Most agent games burn tokens because one expensive model does everything: it reads state, decides, and executes. Split those three jobs across three cost tiers.

Tier 3 — rare

Strategist

The main session, on Opus or Sonnet. You describe your strategy in your own words. It turns that into a machine-readable policy and stores it.

runs: when you say so · cost: high · frequency: minutes to days
Tier 2 — free

Scheduler + executor

Mod code. No model at all. Polls chain state on a timer, caches it, decides whether anything needs a decision, and builds and sends the transaction once a move is chosen.

runs: every tick · cost: zero tokens · frequency: seconds
Tier 1 — cheap

Move picker

Haiku. Gets the stored policy plus a compact state line. Answers with one move. Does not read files, does not call tools, does not hold history.

runs: only when a choice exists · cost: low · frequency: per decision

The key insight is Tier 2. Most ticks need no model. If no mine can be afforded and no planet is idle, the mod decides that in code and spends nothing. The model is called only at a genuine fork.

Single source of truth

Everything reads the cache the tick fills. This matters for cost: a tool call that answers from cache costs the model one round-trip and costs the chain nothing, while a tool that queries Sui on every call adds latency that makes the model retry and spend more.

Reuse the web client's logic, do not fork it

The transaction builders in web/src/services/sui/transactions/ and the parsers in web/src/utils/ already encode the correct BCS handling and PTB shapes. The mod should import that logic, which likely means extracting it into a shared package the web app and the mod both consume. Copying it creates two places where a contract change must land.

5The tool surface

7The strategy loop

The flow you described, made concrete:

  1. You state a strategy in the main session, in plain words: "expand to three planets, then rush thorium, never drop below 200 erbium."
  2. The strong model compiles it into a policy object and calls tw_policy. This is the only expensive step, and it happens once per strategy change.
  3. You arm autoplay with a budget: tw_autoplay on --max-calls 50.
  4. The tick runs on $.clock.every. It refreshes reserves, redraws the pane, and checks the policy's guard conditions in code.
  5. Only at a fork does it call Haiku with the policy and the state line, and take back one move.
  6. The mod executes the move as a PTB, records the result, and redraws.
  7. You watch the pane. When the strategy stops fitting, you talk to the strong model again and the loop restarts at step 1.

Why the policy object matters

A policy in natural language must be re-read and re-interpreted by the model on every decision. A compiled policy — thresholds, priorities, guards — is checked by mod code for free, and the model is consulted only for the part that is genuinely a judgement call. This is the difference between an agent that costs cents per hour and one that costs dollars per minute.

Scheduling beyond the session

$.clock.every lives inside a running session. For play that continues while you are away, the options are Claude Code's own scheduled runs (routines) or a headless session driven by a cron job. UNDECIDED — see §10.

8Mod or MCP

A mod registers its own tools in-process, so an MCP server is not required for Claude Code. The question is whether other clients matter.

Mod onlyMCP onlyBoth
Claude CodeFull: tools, pane, context, schedulingTools only. No pane, no context shapingFull
Other clientsNoneWorks everywhereWorks everywhere
LatencyIn-processOne transport hopIn-process where it counts
OpsNo serverA process to run and versionA server plus a plugin
API stabilityEarly access, may breakStable specExposed to both

Recommendation for review: build the mod first. It is the only path that delivers the pane and the context shaping, which are the parts that make the token economy work. If the MCP server is still wanted for reach, build it later over the same extracted transaction package, and let the mod call it or bypass it.

9Risks

The mods API is early access

Anthropic's README states plainly that hook modules load only where function hooks are enabled, and that the API may change between releases without notice. A mod is therefore not a stable foundation for the repo's main teaching path. Treat it as an experiment beside the web client, never as its replacement.

RiskImpactMitigation
Key custodyAn autoplay loop needs a signing key with no human in the loopTestnet only. A dedicated throwaway key. Never the key that holds anything real. Hard budget caps in tw_autoplay.
Runaway spendA loop that calls a model every second costs money and gasCall budget and gas budget on arming. The tick refuses to run past either.
Shared-object contentionElementSource<T> is touched by every player; bots make it worseBack off on conflict. Do not retry immediately. This is worth measuring as part of the experiment.
Time-dependent readsReserves are computed from the clock, so a cached value is stale the moment it is readCache the formula inputs, not the result. Recompute on render.
FairnessAn agent that plays all night beats a human who does notA design question for the game, not the client. Raised in §10.
Two clients driftContract change lands in the web app but not the modExtract shared transaction and parsing logic before writing mod-side duplicates.

10Open questions

  1. Key custody. Does the mod hold a key, shell out to a configured sui client profile, or refuse to sign and only prepare transactions for you to approve?
  2. Where the loop lives. In-session $.clock.every only, or also a scheduled headless run that plays while you sleep?
  3. Repo or separate. Does the mod live in trade-wars/ as a new top-level folder, or in its own repo so the game repo stays free of early-access code?
  4. Shared package. Is extracting web/src/services/sui/ into a package acceptable now, or should the mod duplicate for a first spike?
  5. Fairness. Is agent play a first-class way to play Trade Wars, or a demonstration mode marked as such?
  6. Does the MCP server survive? If the mod covers Claude Code fully, is there a real second client you want to reach?

11First slice

The smallest build that proves or kills the idea, in order. Each step is testable with claude plugin test.

  1. Read-only pane. /tw opens a pane listing the overseer's planets and live reserves, polled on a timer. No tools, no writes, no model. This alone proves the pane, the read layer and the cache.
  2. One tool. tw_state answers from the same cache. Confirms in-process tool registration and measures the state line's real token cost.
  3. One write. tw_upgrade on testnet with a throwaway key. Confirms the PTB path end to end.
  4. Haiku picks. $.model.complete chooses between the affordable upgrades. Measure tokens per decision and compare against a hard-coded greedy rule as the baseline.
  5. The loop. tw_autoplay with budgets, and the policy object from Tier 3.

Step 4 carries the real finding. If Haiku with a compiled policy does not beat a greedy rule, the honest answer is that the game does not need a model in the loop, and the project keeps the pane and the tools and drops the agent claim.
